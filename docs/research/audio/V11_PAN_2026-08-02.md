# V11 pan — ouverture stéréo après la V10 Boom

Date : 2026-08-02. Statut : **en production** (release `20260802-195837`).
Code : `a11/backend/apps/server/src/audio/v10-boom.cjs`, constante `V11_PAN_WIDTH = 1.5`.

> La V10 Boom n'est pas modifiée. La V11 est une couche posée **après** elle.

---

## 1. Le constat de départ

Djeff, 02/08 : « on n'entend pas bien les violons », et plus tôt « toutes les chansons
c'est la même merde ».

Ce n'était pas une impression. Mesuré sur un rendu réel de production
(`1785657333928-209bf9de-Session-principale`, extrait de 40 s), en écart milieu−côté —
**plus petit = plus large** :

| | largeur | cordes (1–4 kHz) | G/D | repli mono |
|---|---|---|---|---|
| brut Suno | 10.30 | −30.1 | −0.40 | −0.40 |
| après V10 Boom | **11.00** | **−30.1** | −0.30 | −0.30 |

**Le boom resserre l'image de 0,7 dB et n'apporte strictement rien aux cordes.** Il
ajoute 0,5 dB de niveau dans le grave, c'est tout son effet. La plainte avait une
cause mesurable.

---

## 2. Ce qui est parti en production

Une seule insertion dans le graphe ffmpeg, juste avant le limiteur :

```
[mix]stereotools=slev=1.500,alimiter=limit=0.950:attack=5:release=50:level=false[out]
```

| | largeur | cordes | G/D | G/D cordes | repli mono |
|---|---|---|---|---|---|
| brut Suno | 10.30 | −30.1 | −0.40 | −0.10 | −0.40 |
| V10 Boom seul | 11.00 | −30.1 | −0.30 | −0.20 | −0.30 |
| **+ V11 pan 1.5** | **7.40** | **−29.0** | **−0.40** | **−0.10** | −0.70 |
| + V11 pan 2.0 | 4.90 | −27.7 | −0.40 | −0.10 | −1.20 |

`1.5` retenu à l'oreille par Djeff contre `2.0`, qui creuse le centre.

Ce que la V11 conserve exactement : l'équilibre gauche/droite de la source
(−0.40 global, −0.10 sur les cordes). **Aucune** des constructions à base de déphasage
n'a tenu ça — toutes dérivaient d'environ 1 dB. Son seul coût est le repli mono,
−0.30 → −0.70.

**Garde-fous.** `panWidth = 1` n'insère rien du tout : le graphe redevient octet pour
octet celui de la V10, donc le retour arrière est exact. Bornes `[1, 2.5]`. Réglable
sans redéploiement via `VIVY_V11_PAN_WIDTH` (l'ancien nom `VIVY_V10_BOOM_PAN_WIDTH`
reste lu en second, c'est sous ce nom que la valeur est partie en prod le 02/08 avant
d'être renommée).

## 3. L'ordre ne compte pas — et c'est prouvé

Question de Djeff : « la V10 Boom fait une résonance M et le pan doit arriver après,
est-ce que ça va inverser le résultat ? »

**Non, et ce n'est pas une opinion.** Le boom est un filtre linéaire appliqué
identiquement aux deux canaux (`lowpass`, `adelay=12|12`, `volume`, `amix` — rien qui
distingue gauche de droite). Si `G' = h*G` et `D' = h*D` avec le même `h`, alors le
milieu devient `h*M` et le côté `h*S` : un filtre identique sur les deux canaux
**commute** avec toute opération milieu/côté.

Vérifié par différence échantillon par échantillon entre les deux ordres de rendu :

```
boom PUIS élargir   /   élargir PUIS boom
différence : −91.0 dB   (silence numérique)
```

Seule pièce qui ne commute pas : `alimiter`, non linéaire. Il doit rester en dernier,
d'où la place retenue pour l'insertion.

---

## 4. Ce qui a été essayé et écarté

Toutes ces constructions ont été mesurées sur le même extrait. Aucune ne bat
`stereotools=slev`. C'est un résultat négatif, il est consigné tel quel.

| construction | largeur | défaut rédhibitoire |
|---|---|---|
| miroir de pan réel/imaginaire, σ = 0.85 | 10.10 | −0.70 de vrille sur les cordes |
| croix horaire, quart de tour, 2 faces | 8.80 | −0.90 de vrille globale |
| croix horaire, sens inversé / signe imaginaire inversé | 8.80–9.30 | idem, écart de 0,8 dB entre les 4 sens |
| parcours des 4 faces `+R → +i → −R → −i` | 10.60 | aucun gain : ajoute du niveau, pas de largeur |
| injection sur le côté pur (`+P` / `−P`) | 7.20 | +1.00 de vrille sur les cordes, repli −0.80 |
| élargissement bande haute seule (> 150 Hz) | 7.20 | repli **pire** (−0.80) : le grave est déjà mono |
| retards opposés 7 / 15 ms | 7.70 | −1.00 de vrille, repli −0.70, déphasage dépendant de la fréquence |

**Pourquoi le miroir perd.** `G = a·direct + b·tour`, `D = b·direct + a·tour` est
équilibré *en théorie* — `|G|² = |D|² = (a²+b²)|x|²` si `|tour| = |direct|`. Mais
`aphaseshift` n'est pas exactement unitaire en amplitude, donc l'égalité tombe et
l'image penche. Faire passer les deux branches par le même filtre avec des décalages
opposés corrige l'équilibre global (−0.10) mais laisse −0.70 dans la bande des cordes.

**Pourquoi les 4 faces perdent.** Trois faces sur quatre (`+R` au centre, et les deux
quarts de tour qui sont à moitié milieu) versent leur énergie dans le milieu ; seule
`−R` produit du côté, sur un quart du spectre. Le parcours est juste comme opération,
mais l'énergie ne va pas là où on veut. Le gain apparent était un gain de **niveau**
(+1.4 dB de milieu), visible seulement en normalisant.

## 5. Deux pièges rencontrés, à ne pas repayer

### `afir` est cassé sur le ffmpeg de l'EX44

Le filtre rend `−91 dB` (silence) dans **toutes** les configurations : `gtype`
none/peak/rms, `irgain`, `minp/maxp`, `irfmt=mono`, IR depuis le générateur `hilbert`
comme depuis un fichier wav. Test décisif : une IR réduite à **une impulsion** — qui
doit rendre le signal intact — sort aussi à `−91 dB`. C'est le build, pas l'usage.

Conséquence : **pas de transformée de Hilbert disponible en production**. Le générateur
`hilbert` fonctionne (1023 coefficients, crête −3.9 dB) ; c'est la convolution qui est
morte. Repli utilisable : `aphaseshift=shift=…:order=16`, passe-tout IIR dont le
déphasage dépend de la fréquence — pas un quart de tour constant.

### Un canal muet se mesure comme un quart de tour parfait

Une branche silencieuse donne `milieu − côté = +0.00 dB` **exactement**, puisque
`mid = (x+0)/2` et `side = (x−0)/2` sont égaux. C'est précisément la signature attendue
d'un quart de tour parfait, et les témoins encadrants la rendent encore plus
convaincante :

```
mono dupliqué  (0 face)   +67.10 dB
"quart de tour"            +0.00 dB     ← en réalité : canal muet
anti-phase     (2 faces)  −67.10 dB
```

Quatre séries de mesures ont été construites sur ce faux positif avant qu'il soit
détecté. Un filtre silencieux ne lève aucune erreur : le graphe est valide, le rendu
réussit, les fichiers font la bonne taille.

**Règle :** avant de conclure sur un graphe ffmpeg à plusieurs branches, rendre chaque
branche **seule** et mesurer son niveau. Un paramètre qui, mis à zéro, reproduit la
référence au centième ne valide que la branche restée active — jamais celle qu'il vient
d'annuler.

## 6. Deux chaînes coexistent — ne pas les confondre

Le nom des fichiers de sortie induit en erreur.

- **`src/audio/v10-boom.cjs`** — route `POST /api/double-harmonic/v10boom/process`.
  D'où viennent les rendus récents dans `a11-data/runtime/double-harmonic-d40/`
  (`<id>-<titre>-v10boom-input.mp3` en entrée, `<id>-<titre>-funesterie-d40-v10boom.mp3`
  en sortie — le `d40` du nom désigne le **dossier**, pas le module). C'est la chaîne
  que la V11 pan modifie.
- **`src/audio/double-harmonic-d40.cjs`** — appelé par `src/vivy/vivy-layer-apply.cjs`
  (bouton du studio Vivy). Deux couches harmoniques `rubberband` posées au centre absolu
  (`pan=stereo|c0=c0|c1=c0`), à des poids réels de **0.0248 et 0.0221**.

**La V11 pan est branchée sur les deux chaînes** (décision de Djeff, 02/08). La constante
vit dans `double-harmonic-d40.cjs` — que `v10-boom.cjs` importe déjà — donc **une seule
source de vérité**, verrouillée par test. Les couches harmoniques de la `d40` ne sont pas
touchées : la V11 n'ajoute que l'ouverture en fin de chaîne.

**Réserve honnête :** les chiffres de ce document sont mesurés sur la chaîne **v10 boom**.
Le même opérateur sur la `d40` n'a été ni mesuré ni écouté — Djeff a explicitement choisi
de ne pas refaire le cycle de validation. Si le résultat déçoit sur ce chemin,
`VIVY_V11_PAN_WIDTH=1` le neutralise sans redéploiement.

### Le troisième chemin, non branché

`double-harmonic-closed-phase-v8.cjs` appelle `runV10Boom`, qui est **opt-in** via
`VIVY_V10_BOOM_ENABLED`. Cette variable n'est présente dans **aucun** des trois fichiers
d'environnement de production (`compose.env`, `a11.env`, `build.env`), et le conteneur ne
la voit pas. Ce chemin n'applique donc ni le boom ni la V11 pan. État constaté, pas
recommandation.

Deux heures de mesures ont été perdues sur `double-harmonic-d40` reconstruit à la main
avec `volume=0.35` — 23 dB au-dessus des poids réels — en croyant mesurer la production.
**Générer la référence avec le code du module**, jamais avec une reconstruction :
`node -e "require('./src/audio/<module>.cjs')"` imprime le graphe exact.

## 7. Méthode de mesure

Toutes les valeurs viennent de `volumedetect` sur des extraits de 40 s rendus
serveur-side, moyenne RMS en dB.

```sh
# largeur : ecart milieu - cote (plus petit = plus large)
ffmpeg -i X.wav -af "stereotools=mode=lr>ms,pan=mono|c0=c0,volumedetect" -f null -   # milieu
ffmpeg -i X.wav -af "stereotools=mode=lr>ms,pan=mono|c0=c1,volumedetect" -f null -   # cote

# equilibre gauche/droite
ffmpeg -i X.wav -af "pan=mono|c0=c0,volumedetect" -f null -
ffmpeg -i X.wav -af "pan=mono|c0=c1,volumedetect" -f null -

# bande des cordes
ffmpeg -i X.wav -af "highpass=f=1000,lowpass=f=4000,volumedetect" -f null -

# cout du repli mono
ffmpeg -i X.wav -af "pan=mono|c0=0.5*c0+0.5*c1,volumedetect" -f null -
```

Extraction robuste de la valeur (un `grep` trop large attrape le `1` de
`volumedetect_1` au lieu du niveau) :

```sh
sed -n 's/.*mean_volume: *\(-\?[0-9.]*\) dB.*/\1/p'
```

## 8. Honnêteté sur le canon

Les constructions dérivées du canon Prime Spiral — miroir réel/imaginaire, croix
horaire à `π/2`, parcours des quatre faces `+R → +i → −R → −i` — ont toutes été
mesurées et toutes perdent face à trois caractères de `stereotools`. Ça ne dit rien
de la valeur du canon ailleurs. Sur cette question précise, l'outil standard a gagné.

La constante `1.5` n'est pas dérivée du canon et ne prétend pas l'être : c'est une
valeur choisie à l'oreille entre `1.5` et `2.0`, sur une plage bornée par la mesure.

Voir aussi : `docs/research/prime_spiral/MODELE_OPERATOIRE_CANON_2026-05-29.md` (§300,
serrage en croix/étoile), `docs/research/prime_spiral/CONSTANTS_LOCKED_2026-05-29.md`
(`π/2` = une face de croix).
